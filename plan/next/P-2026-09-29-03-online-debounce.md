## 目标与设计边界

一次端口探测失败不应清掉待审批/提问提醒。当前
[`DshStateTracker._apply_online()`](../../pet/dsh_state.py) 立即释放锁存并切 offline，
[`AppShell._on_dsh_state_changed()`](../../pet/app.py) 随即清除所有交互。

建议连续失败阈值先取 N=3，在现有约 3 秒轮询下测量实际判离线延迟后再定值；
这是候选方案，不是已批准的新持久设置。任一候选端口恢复即清失败计数。
**连续探测失败只能证明不可达，不能单独证明进程退出。**
需单独定义可信的会话终止、进程退出或重连对账依据，之后才决定何时清掉交互。
不可达期间旧按钮的可用性和提示也须一起明确。

## 验收矩阵

| 场景 | 通过标准 |
|---|---|
| 审批常驻时失败一次后恢复 | 无 offline 边沿、无提醒清理、失败计数归零 |
| 连续失败达到 N 次 | 一次失联转换；不会仅因端口不可达就断言请求已解决 |
| 全部端口失败后其中一个恢复 | 恢复在线并对账，不重复显示相同 pending |
| DSH 明确退出或旧请求确认失效 | 只按确认的作用域清理，避免影响其它 Agent 的提醒 |
| stop 后后台结果返回 | 不再发状态变化或重建提醒 |
| 首次启动服务未运行 | 明确呈现未运行，不无限保留未知状态 |

## 风险与收尾

较大 N 会延后失联提示，较小 N 不能有效抑制抖动，以实测说明取舍。
